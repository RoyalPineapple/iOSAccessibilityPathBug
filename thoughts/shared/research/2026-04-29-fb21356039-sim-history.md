# Research: Did the FB21356039 reproduction tests previously work on the iOS Simulator?

**Date**: 2026-04-29T11:26:57+02:00
**Researcher**: aodawa
**Git Commit**: 6f13f691a897c9485d1a76d39d73b65bc3209752
**Branch**: main
**Repository**: RoyalPineapple/iOSAccessibilityPathBug

## Research Question

"didnt we have this working on sim before?" — i.e., the `CoordinateDriftDemonstration` and `BugMechanismInvestigation` tests that exercise `UIAccessibility.convertToScreenCoordinates(_:in:)`. The current state on this machine is that all path-based tests return `(0, 0)` on every iOS Simulator runtime tested (17.5, 18.5, 26.3.1, 26.5), while `view.convert(_, to: nil)` still returns the correct screen origin — i.e., `accessibilityFrame` and `convertToScreenCoordinates` appear disconnected from the simulator's accessibility subsystem.

## Summary

**The codebase contains multiple independent pieces of evidence that these tests previously produced the bug-pattern values (1× / 2× / 3× of the view's screen offset) on the iOS Simulator.** The strongest evidence is in commit messages, hardcoded numeric literals in test assertions, the test command published in `FEEDBACK.md` (which directs Apple to reproduce on simulator), and a `setUp` change committed on 2025-12-11 that the commit message describes as "restoring" simulator behavior. No file in the repo carries any "device-only" / "simulator-skip" / `#if targetEnvironment(simulator)` guard, version-availability check, or comment marking simulator output as different from device output.

This research documents what is in the repo, not why the current machine's results differ.

## Detailed Findings

### Commit `b38f03a` (2025-12-11) — explicit claim of simulator behavior

`git show b38f03a --stat` shows three files touched: `iOSAccessibilityPathBug.xcodeproj/project.pbxproj`, the `BugDemonstrationTests.xcscheme`, and `iOSAccessibilityPathBugTests/CoordinateDriftDemonstration.swift`. The diff in the Swift file replaces a bare `UIWindow(frame:)` with a `UIWindow(windowScene:)` that pulls the window scene from the test host app. The full commit message reads:

> Fix test window to use UIWindowScene for proper coordinate conversion
>
> UIAccessibility.convertToScreenCoordinates requires windows to be connected
> to a UIWindowScene for proper screen coordinate context. Tests were creating
> windows without scene context, causing convertToScreenCoordinates to return
> paths unchanged (no conversion).
>
> Fix: Connect test windows to the UIWindowScene from the test host app.
>
> This restores the expected bug behavior:
> - 1st read: 100.0 (correct)
> - 2nd read: 200.0 (2× drift bug)
> - 3rd read: 300.0 (3× accumulating drift)

The `setUp()` lines this commit introduced are still in the file today (`iOSAccessibilityPathBugTests/CoordinateDriftDemonstration.swift:13–30`). The same scene-connection pattern is reproduced in `iOSAccessibilityPathBugTests/CoordinateDriftDemonstration.swift:13–30`.

### Commit `ad39fd0` (2025-12-11) — observed test result count

`ad39fd0` (rename `PathMutationDemonstration` → `CoordinateDriftDemonstration`) carries:

> Tests verified: all 8 tests run correctly with new name (3 fail showing
> the bug, 5 pass on unaffected types/workaround)

The 3-failing-5-passing split matches what the assertion bodies in `CoordinateDriftDemonstration.swift` predict only when `convertToScreenCoordinates` is performing an actual conversion: `test_coordinatesDriftOnRepeatedReads`, `test_cgPathWithQuadCurve_coordinatesDriftOnRepeatedReads`, and `test_cgPathWithLines_coordinatesDriftOnRepeatedReads` would fail (drifting), and the four "stable" tests (rect, oval, arcCenter, copy-workaround) would pass. With no conversion, all 7 tests fail with "0 != 100" — the pattern observed on the current machine.

### Hardcoded literal expected values in `BugModelTests.swift`

`iOSAccessibilityPathBugTests/Exploration/BugModelTests.swift:129–132`:

```swift
XCTAssertEqual(output3.bounds.origin.x, 300, accuracy: 0.1,
    "After 3 calls: X should be 300")
XCTAssertEqual(output3.bounds.origin.y, 600, accuracy: 0.1,
    "After 3 calls: Y should be 600")
```

The view in this test has `frame: CGRect(x: 100, y: 200, ...)` (line context above). `300` and `600` are exactly `3 × (100, 200)` — the third-read value of the bug pattern. These are bare numeric literals in the assertion's `expected` parameter, not computed at runtime.

`iOSAccessibilityPathBugTests/Exploration/BugModelTests.swift:155–156`:

```swift
XCTAssertEqual(mutatedOrigin.x, 310, accuracy: 0.1, "Mutated X should be 310")
XCTAssertEqual(mutatedOrigin.y, 620, accuracy: 0.1, "Mutated Y should be 620")
```

The accompanying comment at line 153 reads: `// Path is now at origin (10 + 300, 20 + 600) = (310, 620)`. Both the literals and the explanatory comment record a specific arithmetic outcome: original path origin `(10, 20)` plus `3 ×` the view's screen offset `(100, 200)`. Writing these literals requires having seen them.

### Diagnostic output strings in `BugMechanismInvestigation.swift`

`iOSAccessibilityPathBugTests/Exploration/BugMechanismInvestigation.swift` carries XCTFail message strings that enumerate the per-read progression at multiple sites:

- Lines 308–313: `"1st: \(r1) (Expected: 100)"`, `"2nd: \(r2) (Expected: 200)"`, `"3rd: \(r3) (Expected: 300)"`
- Lines 131–135: `"Expected: 300" after 3 reads`, `"Expected: 100 if state reset, 400 if not"`, `"Expected: 200" after moving the view to x=200`
- Lines 34, 54, 63, 81, 103–106: similar "Expected: 100/200/300/400" labels for views at x=100 and x=300

These message strings are written by the test author to describe what the test thinks the values should be. They are consistent with the bug's documented `(N × screenOffset)` formula and with views placed at `x=100` and `x=300`.

### `Exploration/` setUp pattern is the *pre-fix* form

The `codebase-analyzer` review of `iOSAccessibilityPathBugTests/Exploration/` (all 13 files) found that every file with an active `setUp()` uses:

```swift
window = UIWindow(frame: CGRect(x: 0, y: 0, width: 400, height: 800))
testView = UIView(frame: window.bounds)
window.addSubview(testView)
window.makeKeyAndVisible()
```

— without a `UIWindowScene`. This is the exact pattern that commit `b38f03a` describes as causing `convertToScreenCoordinates` to "return paths unchanged (no conversion)." So the Exploration tests are running with the older setup. The hardcoded `300/600/310/620` literals in `BugModelTests.swift` therefore cannot have been observed under that setUp from the current state of the world; either (a) they were observed at a moment when this `UIWindow(frame:)` setup *was* sufficient on the simulator, or (b) someone authored the literals from a separate run that used the scene-connected setup, or (c) the values were never observed and are speculative — but the explanatory comment "(10 + 300, 20 + 600) = (310, 620)" reads as descriptive, not aspirational.

### Screenshot filenames suggest simulator origin

The two PNGs in the repo root are `testAccessibilityPaths_17_5_393x852@3x.png` and `testAccessibilityPaths_18_5_402x874@3x.png`. The point-size dimensions `393×852` (iPhone 15 Pro / 16) and `402×874` (iPhone 16 Pro / 17 Pro) at `@3x` match the iOS Simulator's reported screen bounds for those device classes — the `Window screen bounds: (0.0, 0.0, 402.0, 874.0)` line in the current diagnostic run on the iOS 26.5 sim with iPhone 17 Pro is the same `402×874`. The filename convention is consistent with `AccessibilitySnapshot`'s default attachment naming (`<testname>_<os>_<screen>@<scale>.png`) and with the README's note that the screenshots were "Generated with AccessibilitySnapshot."

### No skip/availability guards anywhere

The `codebase-analyzer` sweep of `Exploration/` confirmed no `XCTSkipIf`, `XCTSkipUnless`, `throw XCTSkip(...)`, `#if targetEnvironment(simulator)`, `@available`, or `#available` markers. A repo-wide grep would be needed to confirm this for `CoordinateDriftDemonstration.swift` and the host app, but none have been observed in the files read in this session.

## Architecture Documentation

The reproduction depends on a UIView subclass overriding `accessibilityPath` to call `UIAccessibility.convertToScreenCoordinates(path, in: self)` (`iOSAccessibilityPathBugTests/CoordinateDriftDemonstration.swift:178–188` for the buggy pattern, `:191–201` for the workaround). The harness builds a `UIWindow` connected to the test host app's `UIWindowScene`, places a sub-view at a known screen offset, and calls `view.accessibilityPath` repeatedly. The expected-X computation is `view.convert(view.bounds, to: nil).origin.x + path.bounds.origin.x` (`CoordinateDriftDemonstration.swift:48`), which yields the screen origin if the conversion is being performed and the local origin if it isn't.

The Exploration suite (`Exploration/` + `BugExplorationTests.xctest` target, `BugExplorationTests.xcscheme`) carries an older harness pattern (`UIWindow(frame:)` only) and a denser set of mechanism probes. The two test bundles share the `AccessibilityBugTestHost.app` host (`iOSAccessibilityPathBug.xcodeproj/project.pbxproj:172` for `BugExplorationTests`, line context for `BugDemonstrationTests` further up).
